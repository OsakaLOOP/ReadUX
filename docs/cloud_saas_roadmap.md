# ReadUX 云端分析 SaaS 方案

## 目标与阶段选择

前期以 RunPod serverless GPU 完成部署实验和共同执行核心优化，上线部署比较 RunPod 与恒源云 RTX 4060 Ti 常驻实例。两种模式共用推理核心、镜像和分析协议；常驻部署增加 HTTP 入口。实验阶段由本地脚本直接请求 RunPod，产品阶段再接入账号、订阅与共享缓存。校内 eScience 方案因须经课题组办理，已退出可执行方案。

前期提供全量后台分析，任务提交后由平台分配独立 worker。后期增加按需分析，阅读器优先获取当前范围。性能目标为单卡 3000 token/s，6–10 并发下综合体验达到 300 token/s；经营目标为低固定成本起步，长期月价 15–19 元，年卡进一步优惠，收入达到每月约一万元即可形成合适的运营规模。

本地分析中，GiNZA 调用占 36.3%，查词目标生成占 60.9%。云端主要改善结构精度和推理耗时；查词目标按阅读范围生成和缓存复用，作为独立优化工作推进。

## 模型与 GPU

采用 GiNZA 5.3.0、ja_ginza_bert_large 5.3.0 和 Python 3.12。正式微调权重为 megagonlabs/transformers-ud-japanese-bert-large-ginza，revision 为 7683285d102ba2098cf5f2641388cd69c7406241。模型为 24 层、1024 隐藏维度、16 个 attention heads，共 337441792 参数，safetensors 文件为 1.350 GB。默认采用 FP16，权重占 643.6 MiB，Transformer 输出转为 FP32 后交给 spaCy 结构分析头。

官方精度为 LAS 93.8、UAS 94.9、UPOS 98.3、ENE 70.8。语言质量关注复合词、复杂活用与复杂语法，复用现有来源输出和对齐协议。

实验选择 RunPod 16 GB GPU 档，包含 A4000、A4500、RTX 4000、RTX 2000，价格为 0.58 美元/小时。常驻首选恒源云 RTX 4060 Ti 16 GB，月租 275.40 元，配 8 核 AMD EPYC 7601、32 GB 内存、20 GB 系统盘、50 GB NVMe 数据盘及标示为 800 Mbps 的上下行带宽。雨云 P40 两档实际月租为 168／258 元，后者当前售空。

RTX 4060 Ti 具备 FP16 Tensor Core，加上 16 GB 显存和 32 GB 系统内存，适合复用现有 FP16 推理及 CPU 解码优化。P40 的实际速度低于本机 RTX 3050 Laptop，缺少 Tensor Core，现有 FP16 吞吐目标不能迁移到 P40；雨云 4／8 GB 显存和 16 GB 系统内存进一步限制批处理与并行进程。雨云保留在价格表中，退出满足 3000 token/s 目标的候选。

## Serverless：独立请求与弹性并发

Serverless 上线版本采用优化后的完整 GiNZA 管线，每个 worker 处理一个用户请求。平台按并发请求启动多个 worker；产品配置最少 0、最多 10，覆盖 6–10 个用户同时分析。每个请求独立执行，十个并发请求对应十份计算资源，费用按总 worker 秒数累加。应用直接提交任务，省去业务端的任务队列和调度服务。E1 单请求实验将上限设为 1，并发实验切换到 10。

每个 worker 内采用一份共享 FP16 BERT、一个 GPU 计算流、一个独立 D2H 流和八个 CPU 解码进程。单本书包含的独立文本单元分配到 CPU 执行流，GPU 对这些单元分批计算；CPU 解码批次 A 时，GPU 计算批次 B。worker 内共享预计算特征和结果缓冲区，完成后按单元顺序组合。该执行核心同时用于后期常驻模式。

上线资源预算为每个 worker 八个有效 CPU 核心、24 GiB 系统内存、16 GB GPU，完整吞吐按 3000 token/s 规划。八个 CPU 进程只保存结构分析头和工作缓冲区，BERT 权重在 GPU 进程保存一份。所有进程在 worker 启动时初始化并复用；模型加载、进程初始化和首次预热合计预留 30 s。

E1 的单进程 FP16 管线用于记录零优化基线；E2 必须完成 NER CPU 并行、数组计算与传输优化、GPU/CPU 阶段重叠和批处理配置，完成后进入桌面接入与收费阶段。

## 常驻单卡：共享 GPU 与 CPU 并行

常驻单卡只有一个 GPU 计算资源，6–10 个请求共同使用一份 BERT 权重。推理进程从各请求提取文本单元，组成长度相近的 GPU 批次；CPU 解码进程处理不同单元，结果按请求 ID 和单元 ID 组合。按单元交错服务使每个用户持续取得结果，全书任务持续在后台推进。

常驻复用 serverless 已完成的执行核心，采用一份 FP16 BERT、一个 GPU 推理进程和多个 CPU 解码进程，NER/依存结构头随解码进程常驻。BERT 特征、NER 预计算与 CPU 解码分阶段执行；CPU 进程通过共享内存接收 token 信息和必要特征。恒源云 32 GB 内存可容纳共享模型及解码进程，8 核 CPU 按实际持续性能配置进程数量。每进程 BLAS 线程数为 1，CPU pool 随服务启动并持续复用。

4060 Ti 常驻完整管线的目标为 3000 token/s，6–10 并发的容量均摊为 500–300 token/s。CPU 解码与下一批 GPU 计算重叠，减少本机测量中的 GPU 等待；多个用户共享模型并按单元合批。显存空间已经充足，GPU 计算能力和 EPYC 7601 的 CPU 解码速度决定最终吞吐。

## GiNZA 需要的优化

2026-10-13 的本机优化阶段已完成交接：共享一份 FP16 BERT、CPU 进程池、共享内存、长度排序和双批次重叠已实现，固定 9068 token 语料的同池重叠实验为 2188 token/s，含 JSON 编码为 2019 token/s。现有执行流程、测量变量及 GPU 多流对照集中在 [BERT 优化交接](ginza_optimization_handoff.md)。下一任务分析流程模型并设计 RTX 4060 Ti 16 GiB 配置，重点为 GPU 活跃计算、长度合批、多流稳定性、异步传输和 CPU 供应能力；下表作为完整云端核心的目标范围。

| 对象               | 具体改进                                                                                                                                       | 实施位置与顺序                                    |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| NER CPU 解码       | 独立文本单元并行执行；保留每个单元内 BILUO 动作顺序、合法动作约束和 greedy 选择                                                                | E2 上线前必须实现，serverless 与常驻共同使用      |
| CPU 算法与数据布局 | 现有 Cython 解码继续复用；优化状态特征求和与两路 maxout 的向量化、合法动作筛选与 argmax 的循环合并，复用工作缓冲区；保持原始分数与同分选择规则 | E2 上线前完成，缩短每个 token 的 758 动作处理成本 |
| NER 预计算与传输   | 按实际 token 数生成紧凑特征，合并 GPU→CPU 传输，CPU 使用共享缓冲区；及时释放已完成批次的预计算缓存                                             | 两种模式共用；避免大批次特征与 Doc 同时长期驻留   |
| GPU 批处理         | 按序列长度组织单元，减少 padding；联合调整外层 batch 与 max_batch_items，保留 128/96 分窗语义                                                  | 两种模式共用；常驻单卡合并不同请求的单元          |
| GPU 与 CPU 重叠    | 使用两个批次缓冲区，CPU 解码批次 A 时 GPU 计算批次 B；同步仅发生在对应批次交付时                                                               | E2 上线前必须实现，serverless 与常驻共同使用      |
| Tokenizer 与输出   | 正文准备、tokenizer、Doc 转结果与结构解码按单元并行；输出后释放 Doc 和 Transformer 特征                                                        | 两种模式共用，控制全书任务的内存峰值              |

NER 优化保留完整实体能力和现有模型参数。算法复杂度仍随文本长度线性增长，改进来自每个 token 的动作计算常数、内存访问、独立单元并行和阶段重叠。纯 GPU BERT 已达到目标，优化顺序为 CPU 解码并行、NER 数组与传输、GPU/CPU 重叠、批大小调整。E2 的交付包含独立于平台入口的共享执行核心、CPU 结构头加载、Doc 与特征重建、共享缓冲区交付、单元结果组合，以及完整输出对照；P4 在此基础上增加跨请求的单元合批与优先顺序。

## 两种模式的单次时间预算

本机 FP16 完整耗时约 1.235 ms/token。近似外推将分阶段摘要中的非 Transformer 部分折算为 0.980 ms/token，剩余部分为 0.255 ms/token。两个数是跨实验归一化后的设计预算；第一项包含 NER 预计算、特征传输和 CPU 解码。

基础配置的 GPU 部分按本机两倍速度外推，零优化基线为 0.980 + 0.255/2 = 1.108 ms/token，约 900 token/s。优化后的两种模式均采用六个 CPU 核心、80% 有效效率，非 Transformer 阶段按 4.8 个有效执行流分摊：0.980/4.8 + 0.255/2 = 0.332 ms/token，约 3000 token/s。GPU/CPU 重叠用于降低阶段等待并维持这个吞吐目标，CPU 数组优化用于缩短解码时间。

4060 Ti 的 FP16 GPU 阶段按本机 RTX 3050 Laptop 的两倍速度编列预算：零优化管线约 900 token/s；CPU 解码经六路并行及阶段重叠后，完整管线目标为 3000 token/s，十万 token 书暖机约 38 秒。外推沿用本机 5800H 的有效 CPU 处理能力，恒源云所配 EPYC 7601 的实际 CPU 解码吞吐须在部署实验中单独测定。P40 的已知计算性能低于本机 3050 Laptop，不采用此 3000 token/s 预算。

| 状态                  |        完整吞吐预算 | 9068 token 暖机 | 73500 token 暖机 | 100000 token 暖机 |          冷启动增加 | 使用阶段       |
| --------------------- | ------------------: | --------------: | ---------------: | ----------------: | ------------------: | -------------- |
| Serverless 零优化基线 |  900 token/s/worker |            15 s |             87 s |             116 s |                17 s | E1 实验对照    |
| Serverless 优化版     | 3000 token/s/worker |             8 s |             30 s |              38 s |                30 s | E2 完成后上线  |
| 常驻单卡零优化基线    |      900 token/s/卡 |            15 s |             87 s |             116 s | 服务启动一次约 17 s | 切换时性能对照 |

完成时间采用 N/吞吐 + 5 s，5 s 覆盖请求、结果转换和传输。Serverless 优化版的缓存冷启动完成时间分别为 38、60、68 s；零优化基线分别为 32、104、133 s。冷启动预算从缓存已准备、平台开始启动 worker 算起；常驻服务持续复用已初始化的模型和 CPU pool。

6–10 个 serverless 请求分配独立 worker，每个请求保持优化版的单次时间，聚合吞吐按 18000–30000 token/s 计算。十本十万 token 书在暖机条件下各约 38 s 完成。常驻单卡由十个请求共享 3000 token/s，按单元交错时约 6.4 分钟完成整组，平均每用户约 300 token/s。两种模式的单请求耗时、聚合容量和计费分别计算。

现有实验输出约 5 MB/9068 token、gzip 后约 0.295 MB。一本 100000 token 的同类输出约 55 MB JSON、压缩后约 3.3 MB。网络预算为 100 Mbps，压缩输出传输约 0.26 s，计入固定 5 s。模型缓存的磁盘读取按 500 MB/s、CPU/GPU 传输按有效 8 GB/s 规划，1.350 GB 权重读取约 2.7 s、644 MiB FP16 权重上传约 0.08 s，初始化预算的其余部分用于 Python/模型对象、CPU pool 和预热。16 GB 显存用于批次与双缓冲容量，计算单元和显存带宽影响 GPU 阶段速度，批量传输与阶段重叠减少同步等待。

## 实验架构

本地 Python 脚本 → RunPod 异步任务 API → GPU worker → 本地结果与报告。

本地脚本负责文本准备、提交任务、查询状态、下载结果和汇总费用。RunPod 负责并发 worker 的实例分配和启停。GPU worker 常驻加载模型，在一个任务内部使用批处理完成书籍单元。

实验阶段使用 RunPod API 直接完成简易 API 闭环，存储使用本地 JSON 和压缩结果文件。详细任务见 [首个部署实验](cloud_gpu_first_experiment.md)。

## 两种部署模式的共同设计

共用函数为 analyze(units, options)，输入一组有序文本单元，输出同序的来源分析和任务指标。RunPod handler 调用该函数；后期常驻 HTTP 入口调用同一个函数。模型加载在进程启动时完成，每次请求复用模型。

采用一个镜像，通过启动命令选择 serverless handler 或后期的 HTTP 服务。共用推理代码、模型文件、依赖与结果序列化；传输入口和任务编号由各部署入口提供。

| 内容         | Serverless                         | 常驻单卡                                  |
| ------------ | ---------------------------------- | ----------------------------------------- |
| 调用         | RunPod /run、/status               | 自建 HTTP API                             |
| 并发         | 平台按请求增加 worker              | 同卡按单元交错，GPU 批处理与 CPU 解码并行 |
| 模型生命周期 | worker 启动时加载                  | 服务启动时加载                            |
| 批处理       | 请求内部的 GPU 批次与 CPU 解码并行 | 相同执行核心，增加跨请求单元合批          |
| 计费         | 启动、执行与保留期间的平台账单     | 按月租用                                  |
| 结果         | 相同来源协议与指标                 | 相同来源协议与指标                        |

镜像内保存 Python、CUDA 运行依赖、GiNZA、词典和服务代码。模型优先使用 RunPod cached models；该方式能覆盖 GiNZA 所需的仓库和加载路径时，worker 从缓存加载。另一种交付方式是在构建时下载模型到镜像，两者作为首个实验的缓存方案比较。后期常驻直接使用相同模型目录。

输入保持原文和单元顺序。来源结果沿用 readux.source-analysis.v1，保存 token、compound、文节、句子、小句、依存和实体。桌面继续负责 UniDic 对齐、活用和查词。模型版本与分析选项进入结果身份，共享缓存由产品层维护。

## 产品架构与缓存

产品阶段新增轻量 API 服务，负责登录、订阅、用量、任务记录与共享缓存。用户提交后立即请求 RunPod；任务完成后保存结果，用户重新打开应用可以继续读取。

初期数据存储可采用单机 SQLite 与压缩结果文件。Serverless 由业务服务执行额度和月度预算；恒源云常驻机提供公网网络、磁盘和高带宽，轻量 API、账户与 SQLite 可同机部署，并按优先额度和普通额度安排单元处理顺序。

结果缓存按文本、模型和分析选项复用。模型文件缓存缩短 worker 初始化过程，分析结果缓存直接复用已经完成的工作，两者分别管理。个人笔记、阅读进度和词汇状态独立保存。

网络抓取与预分析安排在用户分析稳定后，依照热门内容的重复访问收益开展。

## 配额与成本控制

订阅用户每周约 10 本书的优先额度，免费用户每周约 3 本书的普通额度。按一本书 10 万 token 规划，分别为每周 100 万和 30 万。成功分析按量结算，结果缓存免费复用。

RunPod 阶段不设免费计算池，免费用户可复用已缓存结果；每周 3 本普通分析额度随常驻服务启用。订阅用户的优先额度按实际分析量计费。常驻阶段，普通任务与闲时分析使用单卡剩余容量。

单请求实验配置为零常驻 worker、最多一个 worker；并发实验及产品配置为最多十个 worker，每个 worker 执行一个请求，任务内部使用 GiNZA 批处理。worker 完成后保留 10 秒，再缩至零。

## 定价与收支平衡

价格按月卡 15 元计算，收入扣除 5% 支付费后，每名订阅用户每月贡献 14.25 元。每人每周 10 本、每本十万 token，100 人全部用满时，每月约 4.29 亿 token。RunPod 优化版按 0.58 美元/小时、汇率 7.2、每本独立冷启动估算：每本 33.3 秒分析、30 秒初始化、5 秒请求及输出、10 秒空闲保留，约 0.091 元；100 人付费额度约 390 元/月，加 200 元固定费用，共 590 元/月。常驻服务器按套餐月租加 30 元/月备份与杂项计算，免费任务使用剩余容量。

## 最优部署比较：RunPod 与恒源云 4060 Ti

两者共用 E2 的 FP16 BERT、NER 解码优化、共享缓冲及长度分组。RunPod 为每个全书请求分配独立 worker，配置 0–10 个 worker；恒源云为一张 4060 Ti 全天服务，跨请求按文本单元合批。恒源云的 16 GB 显存和 32 GB 内存可以容纳共享模型及 CPU pool，性能重点转为所配 EPYC 7601 的解码能力。两种部署以完整管线 3000 token/s 为验收目标。

以十万 token 全书计算，RunPod 优化版单 worker 暖机约 38 秒、冷启动约 68 秒；十人并发可由十个 worker 各自维持此速度。恒源云单卡达到目标时，单人约 38 秒，十人共享时总计约 6.4 分钟，每人平均约 300 token/s。常驻服务在低并发时持续暖机；RunPod 的弹性 worker 保留高峰吞吐。全书后台分析能够使用恒源云的闲时容量，按需范围优先处理在 P4 常驻阶段实现。

100 人付费额度用满时，RunPod 月运行费约 590 元，恒源云含 30 元附加预算约 305.40 元，后者少 284.60 元；对应 15 元月卡平衡人数为 20 人和 22 人。RunPod 固定费用 200 元，加每人约 3.90 元计算费；约 28 名订阅用户用满额度时，总运行费超过恒源云。恒源云月租仅比雨云 P40 旗舰高 17.40 元，同时提供 FP16 Tensor Core、16 GB 显存和 32 GB 内存，因此作为常驻首选。

100 人付费额度在 3000 token/s 下需要约 39.7 小时实际推理，占 720 小时月运行时间约 5.5%。1000 人全部用满额度约需 397 小时，单卡月度容量仍足够；高峰请求与免费额度继续按共享吞吐分配。当前 2000 元/月预算调整为扩容预算，首张常驻卡的计算资源月租为 275.40 元。采购前核对恒源云公网 API 接入、CPU 持续性能、GPU 实际分配方式及月租续费条件。

## 容量与常驻切换

Serverless 上线版单 worker 为 3000 token/s，通过增加 worker 扩展容量；常驻优化管线的 3000 token/s 对应每周理论容量约 18.14 亿，有效容量约 10.89 亿。1000 人每周用满 10 本，需求约 10 亿；使用率 50%、缓存命中率 30% 时，需求约 3.5 亿。1000 用户单卡容量的成立条件是完成 P4 的 GiNZA 内部并行，常驻实例需配套上述 CPU 资源。

1000 人前维持单张 4060 Ti 作为规划目标；第二卡扩容由付费需求和高峰等待决定。19 元月价对应约 527 人时月收入达到一万元，15 元对应约 667 人。

## 后续信息

模型仓库和共同优化核心已确定。Serverless 采用平台 16 GB GPU 档位及 FP16；恒源云 4060 Ti 采用 16 GB 显存及 FP16。采购前确认以下条件：

1. 4060 Ti 的实际 GPU 分配方式、CUDA 驱动版本和 FP16 完整管线速度。
2. EPYC 7601 所分配 8 核的持续性能、32 GB 内存可支持的 CPU 解码进程数量、实例重启后的模型缓存和任务恢复。
3. 公网 IPv4、标示 800 Mbps 上下行、20 GB 系统盘和 50 GB 数据盘的实际套餐配置，以及 API、备份和流量规则。
4. 275.40 元优惠月租的续费条件与实例库存。

RunPod 首个实验继续记录实际 CPU／RAM 配额与总计费时长，用于比较同一优化管线的 serverless 和恒源云常驻成本。
