# GiNZA BERT large 本地 CUDA 测量与输出复核

## 结论

RTX 3050 Laptop 4 GB 已完成 GiNZA 5.3 BERT large 推理、批次上限、精度和量化对照。默认 FP32 完整管线约 1107 字符/s，纯 FP16 约 1319 字符/s；纯 FP16 完整管线的 PyTorch 峰值约 989 MiB。16 GB 显存对这套模型具有充分空间，采购重点可以转向计算性能和租价。

同一正文中，AMP 和纯 FP16 的离散分析结果与 FP32 完全一致。INT8 改变 28 个词位置，NF4 改变 118 个。纯 FP16 兼顾显存和结果一致性，适合列为云端首选候选；AMP 保留为使用原有框架配置的候选。

完整管线主要耗时在 NER。保留 NER 时 BERT AMP 约 849 token/s；关闭 NER 的另一组性能实验达到 4705 token/s。实体识别是否进入产品分析范围，应按功能价值决定。

日期为 2026-10-13，显卡为 NVIDIA GeForce RTX 3050 Laptop GPU，专用显存 4096 MiB，Windows WDDM，驱动 576.80。Python 3.11.9，PyTorch 2.7.1+cu128，CUDA 12.8，spaCy 3.8.16，GiNZA/ja_ginza/ja_ginza_bert_large 5.3.0，Transformers 4.53.2，spaCy Transformers 1.4.0。

## 理论显存

BERT 参数结构为词表 32768、最大位置 512、隐藏维度 H=1024、中间维度 I=4096、24 层。参数精确计算：

~~~text
embedding = 32768×1024 + 512×1024 + 2×1024 + 2×1024
          = 34082816
每层 = 4H² + 4H + 2HI + I + H + 4H
     = 12596224
pooler = H² + H = 1049600
总参数 = embedding + 24×每层 + pooler = 337441792
~~~

| 存储精度 | 参数本体 |
| --- | ---: |
| FP32 | 1287.24 MiB |
| FP16 | 643.62 MiB |
| INT8 理想全部参数存储 | 321.81 MiB |
| 4-bit 理想全部参数存储 | 160.90 MiB |

INT8/NF4 主要量化 Linear 层，实际模型存储还包括浮点 embedding 和量化元数据。本次实际 footprint 分别为 355.63、211.63 MiB。

批处理增加输入和中间结果。设批大小 B、序列长度 S，保留 25 组隐藏状态时占用约 25BSH×单元素字节数；单层普通 attention 矩阵为 B×16×S²，前馈中间结果为 BSI。层间临时数据可复用，峰值由同时存活的张量和工作区决定。

| 序列长度 | FP16 全层隐藏状态/B | FP16 单层 attention/B | FP16 前馈中间结果/B |
| --- | ---: | ---: | ---: |
| 128 | 6.25 MiB | 0.50 MiB | 1 MiB |
| 256 | 12.50 MiB | 2 MiB | 2 MiB |
| 512 | 25 MiB | 8 MiB | 4 MiB |

纯 Transformer 的上限实验显式使用 eager attention、保留 hidden states，形成明确的显存压力条件。完整 GiNZA 使用模型原有的窗口和实际输出配置。两组测量分别回答最大批处理容量和实际应用占用。

## 相同正文的配置摘要

全部保留 NER，batch 16。峰值为 PyTorch 实际分配统计；GPU 总占用另含驱动和框架保留空间。

| 模型与执行配置 | 总耗时 | 字符/s | token/s | PyTorch 峰值 | 模型 footprint |
| --- | ---: | ---: | ---: | ---: | ---: |
| ja_ginza CPU | 20.763 s | 711 | 437 | 0 MiB | — |
| ja_ginza CUDA | 9.279 s | 1592 | 977 | 449 MiB | — |
| BERT FP32 | 13.342 s | 1107 | 680 | 1794 MiB | 1287 MiB |

AMP 使用 FP32 权重及自动半精度计算；纯 FP16 使用半精度权重，Transformer 输出转为 FP32 后供 spaCy pooling 与结构头使用。该转换使完整管线兼容纯半精度与低位权重。

INT8 在本机主要节省显存，完整服务速度收益较小。NF4 的速度接近 AMP，但输出变化更多。FP16 的峰值已低于 1 GiB，当前模型通过更低位量化获得的显存收益对 16 GB 部署的重要性较低。

本地 CPU ja_ginza 是本次同版本对照，历史 151 单元性能记录仍保留原环境与原范围。

## 批大小与显存上限

上限实验设置 PyTorch 分配预算为显存的 80%，约 3.2 GiB，留下桌面和 CUDA 空间。下表为该预算、当前分配器和输入形状下的最大成功批次，失败由真实 CUDA 分配错误确认；最大成功批次重复三次。

| 序列长度 | FP32 最大成功/首个失败 | FP32 峰值 | FP16 最大成功/首个失败 | FP16 峰值 |
| --- | --- | ---: | --- | ---: |
| 128 | 108 / 109 | 3078 MiB | 288 / 289 | 3028 MiB |
| 256 | 52 / 53 | 3220 MiB | 140 / 141 | 3242 MiB |
| 512 | 21 / 22 | 3186 MiB | 57 / 58 | 3246 MiB |

纯 Transformer 的 FP32 128 长度在 batch 16–32 已接近吞吐平台，约 4900 token/s；FP16 128 长度在 batch 32 时约 15944 token/s，512 长度 batch 8–32 时约 12900 token/s。增加批次主要继续占用显存，吞吐收益逐渐减小。

GiNZA 默认 max_batch_items=4096，按外层文档词数×批大小分组，再执行 128/96 的分窗。本次 batch 8 产生两组 24×163、24×156 的实际 Transformer 输入。外层 batch 32 也会拆成更小的计算批次，实际应用通常先达到配置上限。

## NER 算法与瓶颈

GiNZA 使用 spaCy TransitionBasedParser.v2 的 NER 状态类型，以 TransformerListener 接收 BERT 特征。NER 配置 hidden_width=64、maxout_pieces=2、extra_state_tokens=false、use_upper=false，采用 greedy decoding。

NER 使用 BILUO 动作：实体开始、内部、结束、单词实体和实体外部。模型有 189 个扩展实体类别，共 758 个动作。每个 token 的状态特征预先计算，GPU 结果复制到 CPU，再由 Cython 的 _parseC 循环选择合法动作并更新状态。

固定动作集合时，状态步数随文本长度近似线性增长。若将动作数 A 单独列入成本，状态组合、maxout 和动作选择约为 O(nA)，特征预计算约为 O(n×64×3×A×2)。NER 所用的动作空间较大，数据复制、CPU 顺序解码和内存访问共同影响完整执行时间。

同一 7152 字符、batch 8、FP32 的分阶段结果：

| 阶段 | 两次平均耗时 | 占比 |
| --- | ---: | ---: |
| tokenizer | 0.126 s | 2.0% |
| Transformer | 1.699 s | 27.5% |
| parser | 0.186 s | 3.0% |
| NER | 4.017 s | 65.1% |
| morphologizer | 0.069 s | 1.1% |
| compound_splitter | <0.001 s | <0.1% |
| bunsetsu_recognizer | 0.074 s | 1.2% |

NER 阶段耗时包含特征准备、传输和解码。CPU 部分执行时 GPU 等待，因此任务管理器呈现间歇尖峰。图中的共享显存接近零，专用显存持续占用后在结束时释放，符合模型常驻、分阶段执行的表现。
